## 一、架构目标与约束

系统面向班级课表和作业共享场景，架构重点不是大规模分布式处理，而是保证三角色权限、
班级与学期隔离、批量导入原子性和部署维护成本可控。

核心约束如下：

1. 学生、班级管理员和系统管理员使用同一套服务端认证与权限体系。
2. 班级和学期范围由服务端从Session与数据库推导，不信任前端提交的授权范围。
3. SQLite是唯一权威业务数据源，浏览器端不保存权威业务数据。
4. 课程基本信息与上课安排分表，一门课程支持多个时段。
5. 双CSV导入、管理员交接和关键多步写入使用事务。
6. 密码使用Werkzeug哈希；邀请码使用安全随机数且数据库只保存摘要。
7. 当前交付以单体Flask应用为主，不引入无必要的微服务或前端框架。

## 四、前端架构

前端采用原生HTML、CSS和JavaScript。`index.html`服务学生与班级管理员，
`admin.html`服务系统管理员，二者统一通过`static/js/api.js`请求Flask API。

前端职责：

- 展示周视图、日视图、课程详情、作业提醒和考试倒计时；
- 根据已认证角色调整操作入口，但不承担最终授权；
- 为写请求携带`X-CSRF-Token`；
- 处理加载、空状态、参数错误、权限错误、冲突和服务端异常；
- 导出PDF时恢复完整周视图，再调用浏览器打印；
- 保证360px以上视口可用，课表区域独立横向滚动。

前端不得：

- 通过隐藏按钮代替服务端鉴权；
- 使用`localStorage`保存账号、密码、角色、课程、作业或班级权限；
- 将用户输入直接写入不安全的`innerHTML`；
- 通过提交`class_id`、`semester_id`或`role`扩大访问范围。

## 五、后端架构

### 5.1 应用工厂与中间件

`app.py`负责创建Flask应用并注册以下全局能力：

- 为每个请求分配或透传`X-Request-ID`；
- 对`/api/`下的POST、PUT、PATCH和DELETE请求执行CSRF校验；
- 登录和学生激活因尚未建立会话而按设计豁免CSRF；
- 返回`X-Content-Type-Options`、`X-Frame-Options`和`Referrer-Policy`；
- 将HTTP异常转换为统一JSON错误体；
- 对未处理异常记录请求ID，并向客户端返回通用500错误。

### 5.2 身份、角色与范围

`require_roles()`每次从数据库读取当前Session用户，检查账号存在、状态为`active`且角色
匹配。班级管理员与学生的`class_id`来自当前用户记录，当前学期来自唯一`active`
学期；业务接口不接受前端传入的范围覆盖服务端上下文。

### 5.3 业务服务

- 认证模块：学生激活、登录限流、Session恢复、退出和修改密码。
- 课表模块：按当前班级、学期和周次查询课程、作业与考试。
- 课程模块：课程及多上课安排CRUD、教师复用、时间冲突检测。
- 作业模块：班级管理员CRUD，学生只读。
- 导入模块：标准CSV解析、两文件完整校验、事务覆盖和逐行错误。
- 系统管理模块：学期、班级、名单、账号、管理员任命/交接和审计查询。

### 6.5 冲突与错误处理

时间冲突同时满足以下条件时成立：

1. 同一班级、同一学期；
2. 星期相同；
3. 节次区间存在重叠；
4. 周次区间存在重叠。

冲突返回HTTP 409及可读详情。更新课程或安排时排除当前被修改课程，避免与自身旧记录
误判。跨班资源按照接口既有规则返回403或404，不在错误中泄露其他班级数据。

## 七、数据库设计

### 7.1 数据关系

```text
semesters 1 ─── N classes
semesters 1 ─── N courses
classes   1 ─── N users
classes   1 ─── N courses
teachers  1 ─── N courses
courses   1 ─── N course_sessions
courses   1 ─── N homework
users     1 ─── N homework(created_by/updated_by)
users/classes ─── N audit_logs
```

### 7.2 表结构与约束

| 表名 | 主要字段 | 关键约束与关系 |
|---|---|---|
| `semesters` | `name/start_date/week_count/status` | 起始日期必须为周一；周数1至30；条件唯一索引保证一个`active`学期 |
| `classes` | `class_code/class_name/semester_id/invite_code_hash/status` | 班级编号全局唯一；只保存邀请码摘要 |
| `users` | `login_id/student_no/name/password_hash/role/status/class_id` | 登录名和学号唯一；学生/管理员必须绑定班级；系统管理员不绑定班级 |
| `teachers` | `name` | 教师姓名唯一，由课程引用 |
| `time_slots` | `section_no/start_time/end_time` | 预置1至12节显示时间 |
| `courses` | `class_id/semester_id/course_code/course_name/teacher_id/exam_date/remark` | 班级、学期和课程编号联合唯一 |
| `course_sessions` | `course_id/classroom/day_of_week/start_section/end_section/week_start/week_end` | 星期1至7、节次1至12、周次1至30且起止有序 |
| `homework` | `course_id/content/deadline/created_by/updated_by` | 属于课程，随课程级联删除 |
| `audit_logs` | `actor_user_id/action/target_type/target_id/class_id/result/detail_json` | 只追加，禁止记录敏感明文 |

### 7.3 索引与完整性

- `semesters.status='active'`条件唯一索引保证唯一进行中学期；
- `users(class_id)`条件唯一索引保证每班只有一个有效管理员；
- `courses(class_id, semester_id, course_code)`联合唯一；
- `users.login_id`和`users.student_no`全局唯一；
- 课程安排、作业、审计按常用查询字段建立普通索引；
- 每次数据库连接执行`PRAGMA foreign_keys=ON`；
- 课程删除时，`course_sessions`和`homework`通过外键级联删除；
- Schema使用`IF NOT EXISTS`和`INSERT OR IGNORE`，支持空库幂等初始化。

## 八、事务与一致性设计

### 8.1 双CSV导入

1. 同时接收课程和作业文件，并限制整体请求体大小。
2. 使用标准CSV解析器读取UTF-8 BOM、引号和字段内逗号。
3. 完整校验两份文件，确认作业课程编号属于同一导入批次。
4. 检查重复课程编号的课程级字段一致，并检测全部上课安排冲突。
5. 校验全部通过后，在一个SQLite事务中删除本班当前学期旧课程并写入新数据。
6. 任一数据库异常执行`rollback()`，其他班级、其他学期及原数据不受影响。

### 8.2 管理员交接

管理员交接在同一事务内停用旧管理员并启用新管理员，数据库条件唯一索引作为最终一致性
保护。交接不修改班级课程和作业归属。

### 8.3 业务写入与审计

课程、作业、邀请码和系统管理写操作将业务变更与审计记录放在同一事务中提交。操作失败
时二者同时回滚，避免出现“业务失败但审计成功”或反向不一致。

## 九、安全设计

| 风险 | 控制措施 |
|---|---|
| 明文密码 | Werkzeug密码哈希，登录只比较哈希 |
| 邀请码泄露 | `secrets`生成、SHA-256摘要入库、明文一次性返回、重置后旧码失效 |
| 跨班越权 | Session用户和数据库推导范围，SQL同时带班级与学期条件 |
| 学生修改共享数据 | 写接口使用角色装饰器，学生写请求返回403 |
| CSRF | API写请求校验Session中的CSRF令牌 |
| XSS | 前端转义不可信文本，禁止把原始业务数据直接注入不安全HTML |
| 暴力登录 | 登录失败限流并返回统一错误 |
| 会话固定 | 登录/激活成功后建立新的认证上下文和CSRF令牌 |
| 错误泄露 | 统一错误体，不向客户端返回堆栈、哈希或密钥 |
| 敏感日志 | 审计详情禁止密码、密码哈希、邀请码明文和CSRF令牌 |
| 默认生产密钥 | `APP_ENV=production`且仍使用开发密钥时拒绝启动 |

生产环境仍必须实际配置HTTPS、独立`SECRET_KEY`和`SESSION_COOKIE_SECURE=1`，并完成验证。

## 十一、部署架构与当前边界

### 11.1 当前本地运行

```text
Browser → Flask开发服务 → SQLite文件
```

本地启动用于开发、演示和验收，不代表生产发布。

### 11.2 目标生产运行

```text
Internet → HTTPS反向代理/平台入口 → WSGI服务 → Flask应用 → SQLite持久化卷
```

生产部署必须满足：

- 关闭Flask debug；
- 通过环境变量提供独立`SECRET_KEY`和数据库路径；
- HTTPS下启用`Secure` Cookie；
- 使用WSGI服务运行，不直接使用Flask开发服务器；
- SQLite文件位于可持久化且可备份的目录；
- 发布前完成备份、恢复、外键检查和回滚演练；
- 部署后复跑三角色、CSV、PDF、权限与审计回归。

CloudStudio外网部署、访问地址、二维码、生产WSGI/HTTPS、备份恢复和并发压测目前尚未
完成，不能写入“已上线”结论。
